# eBay 竞品插件：图片识别精度提升 + 侧边栏改造

日期：2026-09-10

## 背景与问题

现有插件（v0.1.1）在实际使用中有两个问题。

### 问题一：图片识别不准

用户的实际需求是**找同款竞品**——外形基本一致、材质观感接近、整体看起来是同一个东西、成本档次相当。目标是回答"谁在卖我这款货"，而不是"这个品类都有什么样子"。

当前实现有三处根因：

1. **本地算法比的不是外形。** `popup.js:172-214` 的 `imageFeatures()` 把图片缩到 32×32 计算平均亮度哈希（aHash），再配 4×4×4 的 RGB 颜色直方图。这套特征描述的是"整体明暗分布 + 颜色占比"，与轮廓形状无关。eBay 商品图普遍白底，商品在画面中的占比一变化，aHash 结果就完全不同。

2. **视觉模型只能看到本地初筛的前 5/10 名。** `popup.js:276` 取 `items.slice(0, settings.visionLimit)`。由于初筛本身不可靠，真正的同款商品可能根本进不了模型的视野——模型再准也无从发挥。

3. **一次请求塞入全部候选图。** `popup.js:285-295` 把参考图和 5-10 张候选图放进同一次请求。模型对单张图片的注意力被稀释，这是多图对比任务的已知失效模式。

此外 `content.js:33` 的 `cleanImageUrl()` 清空了 URL 查询参数，导致取到的是 eBay 的 225px 缩略图而非更高分辨率版本，进一步降低了可判别信息量。

### 问题二：插件窗口容易被关闭

Chrome 的 extension popup 在用户点击网页任意位置时必然关闭，这是浏览器的固有行为，无法通过配置改变。

更严重的是：当前所有分析逻辑（图片解码、API 调用）都运行在 popup 的上下文中。popup 一关闭，**正在进行的分析直接中断**，已完成的工作全部丢失。

## 目标

- 图片识别能够真实反映"外形相似 + 材质观感相似 + 成本档次接近"
- 视觉模型能看到全部有效候选，而非被坏掉的初筛所限制
- 插件界面常驻，不因点击网页而关闭，长时间分析不中断

## 非目标（YAGNI）

- 不做自动翻页采集（维持只采集当前第一页）
- 不做参考图手动裁剪框（用户确认参考图只走文件上传，通常是干净产品图）
- 不做右键"设为参考图"、不做剪贴板粘贴（用户确认不需要）
- 不做本地机器学习模型（体积与复杂度不成比例）

## 关键决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 识别范围 | 模型看全部有效候选 | 找同款是高精度任务，本地算法不应决定谁能被看到 |
| 模型调用方式 | 逐对配对，一个商品一次请求 | 模型全部注意力集中在一对图上，消除多图稀释 |
| 界面载体 | Chrome Side Panel | 官方 API，不受网页样式干扰，点击网页不关闭 |
| 本地算法角色 | 只做减法省钱，不做排序 | 阈值宽松，宁可多送模型也不误杀同款 |
| 参考图来源 | 仅文件上传 | 用户实际工作流；不引入裁剪等额外步骤 |

## 架构

### 文件结构

当前所有逻辑集中在 `popup.js`（420 行）：采集编排、图片处理、模型调用、渲染、导出。引入并发队列和重试逻辑后会进一步膨胀，因此拆分：

```
sidepanel.html / sidepanel.js   界面 + 流程编排（取代 popup.*）
lib/image.js                    图片解码、缩放、eBay 大图 URL 推导
lib/local-filter.js             本地粗筛（梯度方向直方图）
lib/vision.js                   单对配对打分 + 并发队列 + 重试
lib/api.js                      endpoint 规范化、Chat/Responses 格式适配
content.js                      页面采集（小改：取大图 URL）
background.js                   图片代理抓取（基本不动）
xlsx.js                         导出（增加分项分数列）
test.html                       浏览器内纯函数断言测试
```

原则：`sidepanel.js` 只串联流程，不含算法细节。每个 lib 模块不依赖 DOM 全局状态，可独立测试。

### 数据流

```
用户上传参考图
   ↓ 提取梯度方向特征（一次，缓存）
点击「采集并分析」
   ↓ content.js 采集当前页 60 个商品（含大图 URL）
   ↓ background 代理抓取候选图 → 本地梯度粗筛打分
   ↓ 按粗筛强度砍掉明显不相关的，剩 25-40 个
   ↓ 并发 5 路，每个商品单独一次请求：参考图 + 候选图
   ↓ 模型返回 4 项分数 + 总分 + 判断 + 理由
   ↓ 实时按总分排序渲染，完成后可导出
```

侧边栏在整个过程中不会关闭，因此长时间并发分析是安全的。

## 组件设计

### lib/local-filter.js — 本地粗筛

**替换掉**现有的 aHash + 颜色直方图。

**梯度方向直方图（HOG 简化版）：**

0. **裁剪归一（实施阶段新增）**：先定位商品在白底中的包围盒，裁剪后按比例缩放到统一尺寸
1. 图片缩放到 64×64 灰度
2. 逐像素计算横向/纵向亮度梯度，得出该点的边缘方向与强度
3. 划分 8×8 网格，每格统计 9 个方向 bin 的加权边缘强度
4. 归一化后得到特征向量，用余弦相似度比对

**关于步骤 0 —— 实施阶段验证发现的必要修正：**

初版实现省略了裁剪归一，直接对整幅图提取 HOG。自检立即暴露问题：

| 对比 | 无裁剪归一 | 加入裁剪归一 |
|---|---|---|
| 同形状不同大小 | 0.257 | 0.941 |
| 不同形状 | 0.598 | 0.000 |

即**不同形状的相似度反而高于同形状不同取景**，方向完全错误。根因是 HOG 按绝对位置将边缘投票到固定的空间网格，商品在画面中占比一变，边缘就落进完全不同的格子。eBay 各卖家的取景习惯差异很大，若不修正会在真实场景中严重失准。

修正后同款判别与异款判别完全分离。这也印证了设计文档中"算法能运行与算法准确是两回事"的判断——该问题无法通过代码审查发现，只能靠验证暴露。

**为什么这个特征对得上"看外形"：** 边缘方向分布直接描述形状本身。圆形物体的边缘方向均匀分布在各角度；方形物体集中在 0° 与 90°。该特征对整体明暗、白底面积、缩放均不敏感。

**颜色特征保留但降权：** 形状 75%，颜色 25%。同款商品常有多个配色，颜色不能占主导。

**只做减法，不做排序：** 计算分数后按阈值剔除，剩余候选**全部**送模型，最终顺序由模型决定。

**阈值宽松 + 可调：** 界面提供「粗筛强度」四档，默认「适中」：

| 档位 | 相似度阈值 | 预期送模型数量（60 个商品） |
|---|---|---|
| 严格 | 0.50 | 约 15-25 |
| 适中（默认） | 0.35 | 约 25-40 |
| 宽松 | 0.20 | 约 40-55 |
| 不筛 | 无 | 全部有效候选 |

阈值为初始值，需在算法有效性验证阶段用真实图片集校准后确定最终数值。

**已知局限（明确记录）：** 本地算法对材质基本无感，对拍摄角度差异大的同款可能误杀。这是选择宽松阈值和提供「不筛」档位的原因。

### lib/vision.js — 逐对配对打分

**每个商品一次独立请求，请求中只包含两张图：参考图 + 该候选图。**

模型按四个维度打分：

| 维度 | 权重 | 判断内容 |
|---|---|---|
| 外形轮廓 | 35% | 形状、比例是否为同一个东西 |
| 结构细节 | 25% | 部件构成、接缝、开口等结构特征 |
| 材质观感 | 25% | 表面质感、光泽、材料类型 |
| 成本档次 | 15% | 做工精细度所反映的价位区间 |

返回结构化 JSON：四项分数、加权总分、判断标签（同款 / 高仿款 / 同类不同款 / 不相关）、简短理由。

**分项打分优于单一总分：** 强制模型逐项检查而非凭整体印象给数；同时使结果可复核——用户能看到"形状 90 但材质 40"这类情况并自行判断是否采信。对竞品调研而言，不可解释的黑盒分数没有决策价值。

**并发与容错：**

- 并发 5 路（可调 3-8），避免触发接口限流
- 单请求失败自动重试 2 次；仍失败则标记「识别失败」，不影响其余商品
- 实时进度显示 `已完成 12/32`，每完成一个立即更新对应行
- 提供「停止」按钮；中断后已完成结果保留且可导出

对比现状：当前实现是单次请求承载全部候选，任一环节失败则整个分析失败。

### lib/image.js — 图片质量

- 参考图送模型前缩放至 512px（现为 384px）
- 候选图从 eBay 推导 500px 版本 URL（现为 225px 缩略图）

`content.js:33` 的 `cleanImageUrl()` 需要改为保留/重写 eBay 图片 URL 的尺寸标识，而非清空全部参数。改动量小，对模型可判别信息量提升直接。

### sidepanel — 界面

通过 `chrome.sidePanel` API 实现，点击扩展图标直接打开侧边栏。

```
┌─────────────────────────────┐
│ 市场调研        [当前页面状态] │
├─────────────────────────────┤
│ 参考图                       │
│ [选择图片]  ┌────┐           │
│             │缩略│           │
│             └────┘           │
├─────────────────────────────┤
│ 粗筛强度 [适中▾] 并发 [5▾]   │
│ 模型设置 ▸ (默认折叠)         │
├─────────────────────────────┤
│ [采集并分析]  [导出 XLSX]     │
├─────────────────────────────┤
│ 已完成 12/32  [停止]          │
│ ▓▓▓▓▓▓░░░░░░░░              │
├─────────────────────────────┤
│ ┌───┐ 商品标题…              │
│ │图 │ #3 · €24.90            │
│ └───┘ 总分 87% 同款          │
│       形87 构85 材90 成80    │
│       "轮廓与接缝一致"        │
└─────────────────────────────┘
```

改进点：

- 模型设置默认折叠（当前占据约半屏，但只需配置一次）
- 参考图显示缩略图预览（当前仅有一行文字，无法确认是否传对）
- 每行显示分项分数与理由
- 状态跨标签页保持：切换标签、翻页后结果仍在
- 参考图持久化到 storage，重启浏览器后仍在
- 分析前显示预计调用次数（如「本次将调用约 32 次」）

### 错误处理

当前为"一处失败、全盘报错"。改为分级处理：

| 情况 | 处理 |
|---|---|
| 采集不到商品 | 明确提示，保留现有诊断信息输出 |
| 单个商品抓图失败 | 该行标「无图片」，其余照常 |
| 单个模型请求失败 | 重试 2 次；仍失败标「识别失败」，支持单独重试 |
| API Key 错误 / 额度不足 | 立即停止并说明原因（重试无意义） |
| 接口地址无权限 | 沿用现有 `chrome.permissions` 动态申请 |

## 测试策略

浏览器扩展无法直接运行常规测试框架，因此：

1. **纯函数单元测试：** 梯度特征提取、相似度计算、endpoint 规范化、模型 JSON 解析抽为不依赖 DOM 的模块，在 `test.html` 中以浏览器内断言方式运行。

2. **算法有效性验证（比单元测试更关键）：** 准备一组已知答案的图片集——同款、相似款、不相关各若干张——跑完整粗筛流程，检查排序是否符合预期。算法"能运行"与"准确"是两回事，此项验证不可省略。

3. **模型层渐进验证：** 先以 2-3 个商品小规模验证请求格式与返回解析，确认无误后再放开全量。

## 迁移说明

- `popup.html` / `popup.js` / `popup.css` 被 `sidepanel.*` 取代
- `manifest.json` 需增加 `sidePanel` 权限，`action.default_popup` 改为侧边栏打开行为
- 现有 storage 中的模型设置（`marketResearchSettings`）保持兼容，用户无需重新配置
- `xlsx.js` 导出增加四项分项分数与判断标签列
